# Write-back Smoke Test

## Overview

The write-back server (`src/EAxWiki/WikiWritebackServer.cs`) is a small ASP.NET server, started via `export-and-serve.ps1 --api-port` or `scripts/serve-api.ps1`, that both (a) calls into EA over COM to persist the change and (b) patches the corresponding `wiki/*.md` file's frontmatter/content so the served page reflects it without a full re-export. A smoke test must check **both sides landed**, not just that the HTTP call returned 200.

## Auth and CORS, so requests don't get silently rejected

- Every `/api/*` request needs header `X-EAxWiki-Token: <token>`. The token is per-output-directory, generated by `ApiTokenStore` and already embedded in every exported page's widget as `data-api-token` — read it from a page's HTML (e.g. `grep data-api-token wiki/Assessments/*.md`) rather than guessing or regenerating it.
- CORS is scoped deliberately narrow (`WikiWritebackServer.cs:79-98`): the server only sets `Access-Control-Allow-Origin` when the request's `Origin` host matches the request's own `Host` header **and** the Origin port matches `--wiki-port` (default 8000). A `curl` test doesn't send an `Origin` header at all, so it bypasses this check entirely — CORS only matters for testing from an actual browser page. Auth token is the real gate for scripted tests; a raw HTTP client can set any Origin it wants (`WikiWritebackServer.cs:106-112`), so token mismatch is the only thing that should produce a 401.

## Endpoints and what "success" means for each

| Endpoint | Method | Body | On success |
|---|---|---|---|
| `/api/status-types` | GET | — | Returns live `t_statustypes` from EA — use this to get a valid status value rather than hardcoding one |
| `/api/status` | POST | `{elementId, newStatus, filePath}` | `newStatus` validated against `/api/status-types`; EA element status updated via COM **and** the file's frontmatter `status:` field updated (`FrontmatterParser.UpdateStatus`) |
| `/api/notes` | POST | `{elementId, newNotes, filePath}` | Notes normalized (`FrontmatterParser.NormalizeNotesHtml`) then written to EA and the page |
| `/api/diagram-notes` | POST | `{diagramId, newNotes, filePath}` | Same as notes, but for a diagram's description |
| `/api/row-notes` | POST | `{kind, elementId, rowId, newNotes, filePath, ...}` | `kind` must be `attribute`, `method`, or `tagged-value`, each requiring different extra fields (see `RowNotesChangeRequest`) — picking the wrong `kind`/field combo is a 400, not a silent no-op |

`filePath` is validated by `TryResolveWikiFilePath` (`WikiWritebackServer.cs:30-39`): it must resolve strictly inside the configured output directory and end in `.md` — a path traversal attempt or wrong extension returns 400 before touching EA at all. Use a real relative path from an existing exported page (e.g. `Assessments/ESG Score.md`), not an absolute path.

## Verifying both sides actually landed

1. Send the request, confirm HTTP 200 and `{"success": true}`.
2. Check `wiki/status/writeback.log` gained a new line for the operation kind (`status`/`notes`/`diagram-notes`/`row-notes:<kind>`) — this is what issue #41's daily digest reads, so if it's missing, `LogWriteback` failed silently even though the write-back itself may have succeeded (it's wrapped in try/catch specifically to never block on logging — see `WikiWritebackServer.cs:48-60`).
3. Re-open the target `.md` file and confirm the frontmatter/content actually changed to the new value — this is the check that catches a COM-side success with a file-patch failure (or vice versa), since the endpoint only reports one combined success/failure for what are really two separate writes.
4. If you have EA COM access in the same session, independently re-read the element/diagram's status/notes directly (not through the wiki) to confirm EA itself was actually updated, not just the file.

## Common mistakes

- Testing with `curl`/Postman and expecting a CORS preflight to matter — it won't; only the token header does for non-browser clients.
- Reusing a stale token from a different output directory — tokens are per-directory (`ApiTokenStore.GetOrCreate(outputPath)`), so a token that worked against one wiki instance will 401 against another.
- Picking a `newStatus` value that isn't in the live `t_statustypes` table — always fetch `/api/status-types` first rather than reusing a value seen in a page's `status_options` frontmatter, which could be stale relative to the EA repository.
- Checking only the HTTP response and not `wiki/status/writeback.log` or the file itself — a 200 response only proves the request was well-formed and initial validation passed, not that both downstream writes succeeded.
